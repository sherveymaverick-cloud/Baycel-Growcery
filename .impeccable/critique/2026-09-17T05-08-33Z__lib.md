## Design Specificity Verdict

**LLM assessment:** The design system tokens and role-based navigation are product-specific. However, the owner dashboard layout (stat grid → approval lists → charts → bottom row) is a category-standard SaaS dashboard pattern. The cashier sales counter with expected/actual cash fields is genuinely grocery-specific, as is the delivery verification per-item flow. The login brand panel with the cart motif is the strongest product-specific element. The floor staff gradient header feels borrowed from food delivery apps.

**Verdict:** The data model is grocery-grounded; the visual composition is 70% interchangeable with any inventory/HR SaaS.

**Deterministic scan:** The detector module is unavailable (missing dependency). Manual scan of 30 Dart files found: 3 hardcoded hex colors, 86 `Colors.*` usages (most contextually correct), 64 hardcoded spacing values, 5 hardcoded EdgeInsets values, ~49 interactive elements missing semantic labels, and 60+ inline TextStyle.copyWith overrides. Key risk areas: `floor_staff_dashboard.dart` (heaviest offender across all categories).

## Overall Impression

The foundation is solid — tokens, role-based architecture, and the delivery verification flow are production-quality. The critical gaps are financial safety (silent payroll deductions), information density (owner dashboard), and incomplete features masquerading as complete (revenue card, reports, search). The single biggest opportunity is **safety and trust** — confirmation dialogs for financial actions, real data wiring for the revenue card.

## What's Working

1. **Design token discipline.** `theme.dart` provides a complete, consistent system (BaycelColors, BaycelTypography, BaycelSpacing, BaycelRadius, BaycelComponents) that's actually used everywhere. The dataMono style for financial figures is a smart product-specific choice.

2. **Role-based progressive disclosure.** `home_screen.dart:77-116` dynamically builds navigation per role — cashier sees only what they need, owner sees everything. Genuinely well-architected.

3. **Delivery verification per-item flow** (`floor_staff_dashboard.dart:1733-1968`). Expected qty vs. received qty with inline validation, discrepancy notes with damaged flag, and two distinct action paths. This is the best-designed feature in the app.

## Priority Issues

### [P0] Sales Counter Short/Over Silently Deducts from Payroll
- **What**: When actual cash < expected cash, the system automatically creates a "Cash Shortage" stock movement that deducts from payroll (`floor_staff_dashboard.dart:253-268`). No confirmation, no preview of deduction amount, no way to contest.
- **Why it matters**: This is a financial penalty delivered as a side effect of a routine submission. A cashier who miscounts by ₱50 gets an involuntary paycheck deduction with no appeal path.
- **Fix**: Before submitting, show a confirmation dialog when short/over is detected: "Your count shows ₱X short. This will be deducted from your payroll. Confirm or recount?" Add a "Report Discrepancy" alternative path.
- **Suggested command**: `/impeccable harden`

### [P0] "Approve All" Has No Confirmation
- **What**: `owner_dashboard.dart:197-211` — The "Approve All" button fires immediately on tap, processing all pending absence requests in a loop.
- **Why it matters**: A single tap approves N requests with no undo. If the owner misreads the count or intends to review individually, they've just committed to all of them.
- **Fix**: Add a confirmation dialog: "Approve all N absence requests? This cannot be undone." with the count clearly displayed. Apply same fix to cash advance bulk approve.
- **Suggested command**: `/impeccable harden`

### [P1] Revenue Stat Permanently Shows "No data"
- **What**: `owner_dashboard.dart:111-117` — "Today's Revenue" shows "No data — Connect sales module" as a static placeholder. This is the first thing the owner sees.
- **Why it matters**: Revenue is the #1 KPI for any business owner. Showing "No data" in the most prominent position signals system failure, not missing configuration. The data exists in Firestore; it's just not wired up.
- **Fix**: Compute revenue from stock movements where type == 'sales' (this data exists — `reports_screen.dart:24` does exactly this). Or hide the card until sales data is available.
- **Suggested command**: `/impeccable clarify`

### [P1] floor_staff_dashboard.dart Is Unmaintainable
- **What**: 2400+ lines in a single file handling 5 different roles, each with 4-6 cards, multiple forms, and complex state management. Contains 13+ TextEditingControllers and role-specific content switches.
- **Why it matters**: A change to cashier behavior could break bodegero stock-out. The nested controller maps are a memory leak risk. This violates single-responsibility.
- **Fix**: Extract each role's content into its own widget file (CashierDashboard, BodegeroDashboard, etc.). The shell should only handle app bar, clock card, and role routing.
- **Suggested command**: `/impeccable distill`

### [P2] Reports "Generate" Delivers a Dialog, Not a Report
- **What**: `reports_screen.dart:372-395` — Tapping "Generate" opens an AlertDialog with 3-5 key-value pairs. No chart, no table, no export.
- **Why it matters**: "Generate" implies producing output. A dialog with "Today's Sales: ₱0" doesn't meet the expectation set by the card description.
- **Fix**: Navigate to a full report screen with charts and export options, or rename to "View Summary". PDF export is table-stakes for a grocery management system.
- **Suggested command**: `/impeccable shape`

## Questions to Consider

1. **If the revenue card is permanently empty, what exactly is the owner monitoring?** The dashboard's primary value proposition collapses. Is this a dashboard or a to-do list for approvals?

2. **Why does the cashier have more form fields (5 in sales counter) than the owner has decision points?** The cashier's cognitive load exceeds the owner's. Is the hierarchy inverted?

3. **What happens when a delivery checker reports a discrepancy but the bodegero needs to stock-in the 7 good items?** There's no workflow for partial receipt.

4. **The "Run Payroll" undo uses a snackbar with a timeout.** If the owner walks away for 30 seconds, the undo disappears. Is a time-limited undo appropriate for a financial operation?

5. **If every role sees empty states on day one, is there a setup/onboarding flow?** Or does every screen show empty states simultaneously?
